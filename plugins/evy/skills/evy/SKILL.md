# Working with EVY

EVY holds the person's spaces (one per company or area of life), with their goals, initiatives, responsibilities and tasks. A folder on this Mac can belong to a space. In such a folder your session starts with that space's context: open tasks with their ids, the person's standing instruction, recent decisions and the progress summary. If it did not, call `get_context`.

## While you work
- Start an EVY task only when the person asks, when it is queued for you, or when your brief opens with its start line ("Start EVY task N3 (<id>)"): then `get_task` that id and work from it. Call `claim_task` first, with the session id from your context, so no other session takes it. EVY then shows the person whether this session is working or waiting on them, from your tool calls and the end of each turn. A claim with no sign of its session for a day goes back to To do, so report before you stop for good.
- Finish it with `report`, in plain words: `headline` is one sentence saying first what is live, merged or still undone; `needs_you` has one short line for each thing only the person can do (a review or merge still to come counts) and stays empty otherwise, because yellow is only for tasks that wait on the person; `worth_a_look` has optional checks and caveats, one short line each; `details` holds everything you did and checked, folded behind one link; `state` is your proposal (done, worth_a_look, needs_you, blocked) and EVY settles the real one. A report with no headline is refused: retry with one. The result is for someone who saw nothing before. A file only when the format matters (a table or matrix as an .xlsx sheet, a letter or contract as a .docx, a deck, an image), with an `OUTPUT:` line, and the result then says in 2 to 4 sentences what it holds, what is open and where it is. An email, post, answer or research goes in the result in full. Never a Markdown file. Status `blocked` when you cannot go on.
- Only the person can answer something: `ask`, one question, then stop. When the answer is a choice, send 2 or 3 `options` (a short name, one line each, your recommendation marked) so they can tap one.
- Work you spot outside your task: `propose` it, for the person to decide. `add_task` only when the person asks for a task, and for an agent only when they asked you to hand the work off.
- A task you add or propose goes to an agent (you, by default) with a `prompt` a fresh session can run from on its own (the task, the files or area, what done looks like) and a `done_when`. It goes to the person (`assignee: me`) only when it needs them, and then says why in `needs_person`: `decision`, `sign_in`, `payment`, `physical` (a call, a visit, a signature), `check` (one only they can make) or `asked` (they asked for it to be theirs). EVY refuses a task for the person without one.
- A plan with steps for later sessions or for the person goes into EVY with `add_plan`, as well as any file you write it in: a title, why, and the steps in order, each with a short `handle`, a `title`, a `prompt` and `done_when` for an agent, `after` (the handle of the step it waits on), its `lane` and, in a git repository, its `worktree`. Each step becomes a task chained to the one before, and EVY draws a Plan document from them in the person's Drafts. Steps that exist as tasks already are adopted with `task_id`. An agent's step that waits on another starts by itself once that one is done; pass `start_by_itself: false` when you or the person start each step.
- A concept, plan or planning session that names later sessions saves them with `add_plan` before it reports, whether or not it also writes them in a file. EVY reads every final report for later steps with no task and offers the person to add them; saving them yourself is better, because you know their prompts.
- Before working on a step of a plan, claim its task. When you start another session for a step, its brief opens with the step's start line (in `add_plan`'s answer and on the task) and ends with `report`.
- A single Claude session the person wants to queue (a build or research session, run later or after another one) is `add_task` with `session: true`: the title starts with a short handle ("B7 · What EVY does with calendar data"), `prompt` is the full session brief, `done_when` says what exists at the end, and in a git repository `worktree` names the base branch (for example `feat/compass`), so it runs in its own worktree beside other sessions. It goes to @claude with a limit of 12 hours, and the person starts it from To-do with Run. With `after_id` it starts by itself once that task is done.
- Splitting an EVY task off into its own session (Claude's desktop app can): only a task you have not claimed, since one you hold stays with you. Open that session's brief with the task's start line. The new session calls `claim_task` with its own session id (from its context, or a short name of its own when there is none) and reports the task itself; the session that started it does not.
- Never tick off the person's own tasks. Say what you did with `comment`.
- You may change only the space of the folder you work in. Read the others when asked.
- A folder that belongs to no space: ask the person which space, then `link_folder`.
- An image: `make_image` uses the person's own image key and gives you the command that saves it where EVY's file rules put the task's files (on Codex, use Codex's own image generation instead). Give it an `OUTPUT:` line in the report.
- The space's notes: when your context names where they are on the Mac, the space's shared notes are Markdown files there: EVY's numbered folders at the top of the space folder (`00 Start here.md`, `03 Plans` to `08 Team context`, the person's own in `02 Private notes`), or a `Knowledge` folder on an older EVY Desktop. Search them (grep) before asking EVY or the person. They are a read-only copy: write notes with `save_note`, and finish a task with `report`. A change made in those files is set aside and EVY's version comes back. The plugin refuses the edit. `knowledge_search` also finds the person's private notes and matches by meaning; `knowledge_page` reads one, with `as_of` as it read on an earlier day.

## Keeping EVY current
- The person decided something with you: `record_decision`, what and why, at most 40 words.
- Where the space stands changed: `update_progress` with the whole summary, at most 150 words. Start from the summary in your context and change only what changed. EVY turns away anything longer.

## Writing for EVY
- One plain fact per line: what changed, what was decided and why, what comes next.
- No account of the work itself, no restating the task, no headings or bold inside a line.
- Facts that are not EVY's (code, documents) belong in the project's own files.
